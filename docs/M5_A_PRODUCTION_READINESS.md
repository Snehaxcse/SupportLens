# SupportLens M5-A production readiness

## Readiness verdict

**NOT READY for public customer production.** The current release explicitly refuses production database configuration. Real-customer AI also requires approval of knowledge rights and provider data handling. Retention, deletion and recovery procedures need owner approval before accepting real customer data. The confirmed anonymous oversized-request blocker was fixed during this audit.

The audit checkpoint is `main` at `8a1d838a911ee48461f1a9dffc3da10c1338889b`. This matched both the local `origin/main` tracking ref and the GitHub branch. The M1–M4-E code and documentation are present. All 48 protected hashes matched and the M1 verification CLI loaded the trusted classifier. The baseline passed 447 offline backend tests and 99 frontend unit tests. A guarded read-only Neon check matched every prior row fingerprint in both databases. Both retained verified TLS, UTC, revision `20261116_0003`, zero model-metadata differences and all 12 database guards. `Decisions.md` and `frontend/AGENTS.md` were intentionally untracked.

## Security, privacy and AI controls

Firebase verifies the project-bound ID token with revocation checking and zero clock skew, requires a verified email and derives identity from trusted claims. Active CUSTOMER/AGENT authorization comes from PostgreSQL. Ticket repositories recheck actors inside transactions, scope customer reads by owner and filter the customer feed to public messages and public event types. Customer response models do not serialize draft, cache or internal-note state. The agent knowledge and drafting routes use an independent agent dependency. Filtered SQL uses bound input or SQLAlchemy operators, and SSRF paths were absent in the inspected knowledge implementation. Source URLs are checked for HTTPS and rendered as links. React renders customer and agent text as escaped text. The CORS configuration requires configured exact HTTPS origins or explicit local HTTP origins and does not enable cookies. Validation messages and request logs omit input values, raw paths and bearer tokens.

The M1 artifact is a digest-pinned scikit-learn TF-IDF/logistic pipeline. It uses joblib on trusted bytes after digest checks. The MiniLM embedder uses a separate digest-pinned, quantized ONNX asset of 23,046,789 bytes and a 466,247-byte tokenizer, with 384-dimensional output. This distinction matters in build and supply-chain reviews. Workflow policy escalates sensitive, uncertain and unsupported intents and takes the stricter of the workflow threshold and the classifier advisory threshold. Index eligibility ties a chunk to an exact published, indexed revision. The prompt treats content as untrusted. Gemini selects evidence sentence IDs or abstains. The server validates IDs and builds extractive text from allowed evidence. Exact extraction limits fabrication but does not establish source authority or contextual relevance. Pattern-based guards cannot guarantee PII removal or rejection of all prompt injection.

The opt-in provider sends a bounded, scrubbed ticket context (up to 1,800 characters) and a list of candidate evidence sentences. The local context can include the subject, description and relevant public discussion, with internal notes excluded. The provider call uses the fixed Developer API endpoint and allowlisted model, bounded timeout/output and no paid fallback or tools. Persisted reservations account for attempts against a configurable Pacific-day cap. Provider quota/failure responses lead to controlled failure and agent handling. App configuration can gate local use. It cannot enforce a cloud account's billing status. Owner-side billing and applicable regional terms need verification before any approved deployment. The current provider's unpaid terms describe product-improvement use and potential human review with stated regional exceptions. [Google AI service terms](https://ai.google.dev/gemini-api/terms), [Gemini model pricing](https://aistudio.google.com/docs/pricing#gemini-3.1-flash-lite).

An agent must independently edit or review, approve the exact draft version and confirm public send. Send revalidates freshness and workflow under lock and replays the same stored public message for an equivalent retry. The cache remains opt-in by default, excludes sensitive and uncertain cases and requires separate agent approval of reusable guidance. Candidate validation checks scope, source policy, versions, similarity, expiry and exact evidence lineage. Reuse creates an independent draft for the target ticket. Invalidation, approval, send and cache use serialize against source/evidence changes. Public delivery remains a human action.

## Database and worker reliability

The three additive Alembic revisions, database FKs, uniqueness constraints and audit triggers enforce the domain contracts. Schema and privileges are checked through guarded PostgreSQL preflight. Local connections require hostname and certificate verification and channel binding. The default connection and statement timeouts are both 10 seconds. Development and test were confirmed as distinct identities. The runtime uses SQLAlchemy NullPool and closes checked sessions. Agent actions lock mutable rows, and the paired message and audit event commit atomically. Knowledge, classifier and draft workers claim durable lease tokens with row locks and skip locked jobs, perform expensive work outside transactions and fence stale completions. Cache evidence and usage are committed with the ticket-scoped draft and public actions recheck evidence. The deployment owner needs to choose free-tier connection and polling budgets and run a restore drill before production.

## Hosting and cost

The feasible ₹0 target is a low-volume synthetic portfolio demo, or an operator-managed local/private demo. Keep real customer onboarding outside that profile until readiness gates are resolved.

- **Next.js.** Build from the reviewed lockfile with the pinned compatible Node runtime and expose only public Firebase web config and the API origin. Vercel Hobby is an option for personal noncommercial use within quotas. Keep running worker processes off the frontend host. [Vercel Hobby](https://vercel.com/docs/plans/hobby).
- **FastAPI and workers.** Use a persistent process with one worker-enabled replica initially, built from pinned Python runtime/dependencies and provisioned verified model assets. Retain PostgreSQL as the durable store and avoid local state assumptions. Render Free web services idle after 15 minutes, may take about a minute to wake and lose local filesystem changes. Free instances do not cover a dedicated background worker. Measure peak Linux RSS before fitting the service to a 512 MB instance. An idle free service can host a delayed synthetic demo. It does not establish dependable background processing. An operator-managed persistent host is an option if its capacity, network, security and operations are approved. [Render free services](https://render.com/docs/free), [Render pricing](https://render.com/pricing).
- **Neon.** The current published Free plan documents 100 CU-hours per project per month, scale-to-zero after five idle minutes and limited storage/transfer/restore. At 0.25 CU, a single continuously active compute in a 30-day month would use about 180 CU-hours. Three 30-second pollers can prevent inactivity while the host is running, so measure and revise the polling budget with approval. Keep production roles isolated and rehearse encrypted backups and restores. [Neon plans and restore limits](https://neon.com/docs/introduction/plans).
- **Firebase and Gemini.** Configure exact authorized deployment domains in an isolated Firebase project. The published Spark limits include 1,000 verification emails and 150 password-reset emails per day. Use Gemini only for approved synthetic payloads while billing is disabled and limits permit. The published Gemini 3.1 Flash-Lite standard text input/output has a free tier. Confirm the actual project limits at rollout. Quota exhaustion should leave manual handling available. Review current provider terms before any live customer processing. [Firebase Authentication limits](https://firebase.google.com/docs/auth/limits), [Gemini pricing](https://aistudio.google.com/docs/pricing#gemini-3.1-flash-lite), [Gemini rate limits](https://aistudio.google.com/docs/rate-limits), [Gemini terms](https://ai.google.dev/gemini-api/terms).

₹0 is an infrastructure and API target for the controlled profile, with no guarantee of 24/7 availability. Quota suspension, log/history limits, domain and operator costs, cold starts, and recovery requirements remain relevant. Reliable continuously active managed workers at ₹0 were not established. The M5-C prerequisite is an approved profile, not billing activation.

## Critical remediation and test evidence

**P0-03 remediated.** The HTTP boundary now enforces a 1,310,720-byte (1.25 MiB) body limit before request parsing and dependency evaluation. A declared oversize body is rejected before the first read. The counter stops streamed input at the first chunk that crosses the limit, including when the length is omitted or understated. The API returns 413 `request_too_large` with a generated request ID, safe logging, no-store headers and configured CORS behavior. The limit permits the largest knowledge article and its provenance fields under JSON surrogate-pair escaping. The fix changes only application ingress behavior and requires no schema changes or new dependencies.

The focused authentication/API run passed 58 tests, including five new cases for declared and streamed over-limit requests, the exact accepted limit, and a maximum-sized escaped knowledge article. The Starlette test client reported its existing `httpx` deprecation warning.
